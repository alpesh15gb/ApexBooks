## Run locally

Install `backend/requirements.txt`. Set a unique `JWT_SECRET` of at least 32 characters before migrations or startup, including SQLite development: generate one with `python -c "import secrets; print(secrets.token_urlsafe(48))"`, then export it in your local shell or load it from your private environment configuration. Keep that value stable across restarts and never commit it. The API refuses missing, short or example-placeholder secrets. Then run `python migrate.py` and `uvicorn main:app --reload` in `backend`. Run `npm install` and `npm run dev` in `frontend`. Open `http://localhost:5173/`. The local API defaults to an SQLite file for development. Vite proxies `/api` to port 8000.

## Run with Docker on a VPS

The existing production VPS uses the isolated deployment in [deploy/vps](deploy/vps/README.md), loopback ports 18090/18091 and system Nginx. It retains the existing hosted PostgreSQL database. Follow that deployment guide for this server. The root `docker-compose.yml` is a separate development/fresh-install stack with its own PostgreSQL volume and startup migrations; do not use it to upgrade the current production installation. Keep private environments out of source control.

Optional OCR requires a server-side `OPENAI_API_KEY` for OpenAI, or `OCR_BASE_URL`, `OCR_MODEL` and `OMNIROUTE_API_KEY` (the current preview uses the `OMNIROUTE` alias) for an OpenAI-compatible OmniRoute gateway. OCR endpoints must use HTTPS. Plain HTTP is allowed only for explicit loopback hosts during local development; the legacy `OCR_ALLOW_INSECURE_HTTP` setting no longer permits public HTTP. Invalid transport makes OCR status unavailable with a configuration message, without sending an invoice image or provider key. Without a configured key, purchase entry remains manual. OCR sends a user-selected image through the configured Responses API, returns a reviewable draft, and does not post a transaction. The payload uses image input and structured output as described in the [official OpenAI image guide](https://developers.openai.com/api/docs/guides/images-vision) and [structured output guide](https://developers.openai.com/api/docs/guides/structured-outputs); [OmniRoute documents its Responses route](https://omniroute.hagicode.com/en-US/reference/api-reference/). Test the chosen gateway model's image and structured-output support before relying on it.

## Vercel preview deployment

`vercel.json` runs the Vite frontend and FastAPI backend in one Vercel Services project. This uses the Services beta and is intended as an interim preview while the VPS deployment is prepared. It requires an external PostgreSQL database; the Docker database is local to the VPS and cannot serve Vercel Functions.

The retained preview is [apex-books-preview.vercel.app](https://apex-books-preview.vercel.app/) in the connected Vercel account, with application sign-in and company access checks. Production is [apexbooks.in](https://apexbooks.in/). Both retain the existing hosted PostgreSQL data; sessions are scoped to their server origin. Source files were deployed through the Vercel API; this project is not connected to a Git repository, so later preview changes require a new deployment.

Set `DATABASE_URL` and a unique `JWT_SECRET` of at least 32 characters for Preview. `DATABASE_URL` may start with `postgresql://` or `postgresql+psycopg://`. Apply migrations to the target database with `python migrate.py` from the `backend` directory before deploying. Keep database and OCR credentials in Vercel environment settings, not in source files. For OmniRoute, set `OCR_BASE_URL` to a URL ending in `/v1`, `OCR_MODEL=APEXV1`, and an OmniRoute key as a secret. Any previously configured non-loopback HTTP gateway must be replaced by an HTTPS endpoint before OCR works with this updated source. No live gateway settings are changed by these source changes; manual purchase entry remains available while OCR is unconfigured. A synthetic bill was successfully converted to a reviewable draft with supplier, date, item, quantity, rate, GST rate and source total. This preview configuration does not provide database backups or offsite retention; arrange those at the database provider before putting real books into it.

## Available workflows

- Account registration and sign-in; multiple companies per account. Sign-out revokes the server session, and changing a password ends all existing sessions. A company owner can add an existing registered user as an editor or viewer. Access checks cover reads, writes, exports, OCR and bank reconciliation.
- GST regular, composition or unregistered company setup and owner-edited company details. Multi-line sales invoices, estimates, proformas, cash/bank POS receipts, purchase bills, purchase orders, expenses, linked credit/debit notes, and invoice/bill payments. Line discounts reduce taxable value and appear on PDFs. Estimates, proformas and purchase orders can be converted once into posted invoices or bills after review. Non-GST sales cannot charge GST. Composition sales issue a bill of supply, cannot charge customer GST, and are limited to the company's state in the basic workflow; supplier GST is included in cost for composition and unregistered purchases. Regular GST outward lines can be explicitly classified as taxable, nil rated, exempt or non-GST; wholly non-taxable sales produce a bill of supply. Mixed taxable and non-taxable posted outward documents are blocked until a reviewed combined-document flow is available. Regular GST purchases let the user mark each supplier-tax line as pending input-credit review or ineligible; ineligible GST is carried into inventory or expense rather than the pending-input ledger.
- New financial transactions post balanced journals atomically. Receipts and payouts can be allocated across multiple invoices or bills for the same party; linked notes apply to one document. Remaining balances reflect both older and split allocations. Manual journals, reversals, trial balance and an owner-controlled forward-only period lock are available in the app.
- Dashboard sales, purchases and receipts use posted transactions for the current April–March financial year through today. Sales and purchases are net of credit and debit notes, respectively, and use the same source as the transaction summary report.
- Cash/bank transfers post balanced entries. Create named bank accounts and select one when recording bank payments, POS receipts, expenses, transfers and statement imports. The cash and bank book reads ledger movements, including manual journals and reversals, with date filters, opening/closing balances and PDF/XLSX exports. Bank statement CSV import has duplicate detection and manual allocations across posted transactions in the same bank account, including split deposits and payouts. Both the statement line and payment amount are capped; the previous exact matches remain readable and removable. The legacy bank clearing account remains available for existing records. Reconciliation compares statement and ledger closing balances through a chosen date using an entered statement opening balance. The payment picker ranks suggestions from amount, date, reference and party name, and the user confirms every allocation. Company opening balances are entered separately from the statement opening balance used in reconciliation.
- Posted sales/purchase registers, transaction summary, GST analysis by supply class and rate, financial, party, item activity, document-level receivable/payable ageing and tracked stock reports with PDF/XLSX export. GST analysis uses posted document tax snapshots and labels input tax as pending review or included in cost; it is not a filed return. Ageing uses a selected as-of date and applies dated receipts, payouts and linked notes to invoices and bills; its XLSX export contains numeric amount cells. The stock report shows quantities and moving weighted average cost for newly tracked items. A tracked item can receive one dated opening-stock posting before its first purchase or sale; the value posts to inventory and opening equity. Later count adjustments post inventory gains or losses with a reason, and decreases use current moving average cost. Five selectable company-level document PDF layouts, with supplier details saved at document creation. Transaction register exports are also available.
- Company-specific document prefixes and April–March sequence numbers. Optional image OCR for purchase bill drafts.
- Party and item masters with editable details, party phone/email, CSV templates, preview/import with duplicate skipping, and XLSX/PDF list exports. Master names and an item's stock-tracking setting remain fixed after creation to preserve existing links and stock history. Items may opt into stock tracking. Documents link selected item masters explicitly; tracked purchases post inventory at cost and tracked sales post cost of goods sold using moving weighted average. Linked notes adjust quantities and cost, and postings that cause a negative daily stock balance are rejected. Tracked stock documents must be posted in date order.
- Owner-only company JSON export and portable backups, with optional password encryption. Company restore creates a separate company, remaps identifiers and retains restore lineage; account credentials and team access are excluded. This differs from the whole-database VPS dump below.
- Owner-only activity log records company settings, master imports, posted documents, journals, period locks and bank matching in the same database transaction as each change. It is an operational audit view, not a tamper-resistant external log.
- Whole-database backup and restore scripts for the root local-Compose PostgreSQL deployment: `deploy/backup.sh` and `deploy/restore.sh`. They require explicit `APEX_BACKUP_SCOPE=compose-local` and reject external/ambiguous targets; they are not a hosted PostgreSQL or Vercel database recovery procedure. These contain all tenants. The local backup is published only after a successful dump; `bash deploy/test-backup-safety.sh` checks failure handling with a simulated database. An optional encrypted offsite workflow using age and rclone, including a systemd timer and restore drill instructions, is described in `deploy/SECURE_BACKUP.md`. It must be configured and tested against the actual VPS and storage provider. The older local backup timer writes unencrypted files. Restore requires `RESTORE_CONFIRM=REPLACE_APEX_DATABASE`.

- Posted documents can be cancelled with a reason (ledger reversed, stock and balances released, number kept); invoices and bills can record their first receipt or payout in the same step; formatted Profit & Loss and Balance Sheet statements are available alongside the account-balances report. See [the 1.5 candidate notes](docs/RELEASE_CANDIDATE_1_5.md).

## Known gaps before live use

- Older prototype records remain visibly marked as unposted and are excluded from ledger reports. No automatic backfill is performed.
- Tax logic covers ordinary inclusive/exclusive-price domestic GST, user-selected nil-rated/exempt/non-GST line classes, discounts recorded per line before or at supply, and basic composition billing restrictions. The app does not determine the correct legal class for an item; [CBIC defines exempt and non-taxable supplies](https://cbic-gst.gov.in/hindi/CGST-bill-e.html), and [Rule 49 describes the bill of supply](https://cbic-gst.gov.in/pdf/cgst-rules-30122017.pdf). Composition eligibility, turnover obligations, returns and other special cases are not automated. Post-supply discounts, cess, reverse charge, exports, automatic exemption decisions, e-invoicing, e-way bills, automatic input-credit eligibility and apportionment, and GST filing need separate implementation and current legal review. The purchase credit choice is a user classification, not a legal eligibility determination or a credit claim; [CGST Act sections 16–17](https://cbic-gst.gov.in/pdf/CGST-Act-Updated-31082021.pdf) contain conditions and restrictions. The GST summary is a preparation aid, not a statutory return. The bill-of-supply restriction follows the [CBIC composition guidance](https://cbic-gst.gov.in/sectoral-faq.html) and [composition rules](https://cbic-gst.gov.in/hindi/composition-rules.html); discount treatment follows [CGST Act section 15(3)](https://cbic-gst.gov.in/pdf/CGST-Act-Updated-31082021.pdf).
- Item activity groups descriptions and HSN/SAC codes; the separate tracked stock report uses item IDs and shows cost value. Existing items and old documents are not automatically converted to tracked stock; pre-valuation stock movements are marked unvalued and block later valued postings until migrated. Party statements and payment allocations match names as text. Party-specific ledger accounts and broader GST-advance cases remain incomplete. Stock valuation covers basic count gains and losses but does not cover production, landed-cost adjustments, transfers between locations, lower-of-cost-and-net-realisable-value write-downs or arbitrary legacy stock formats. Depreciation is not calculated. Moving weighted average is a supported cost formula under [ICAI AS 2](https://indasaccess.icai.org/Volume-III/AS/asb.html?a=105), but the business's use of that formula still needs accountant review.
- PDF layouts support company logos and optional signature images. An uploaded image is not a cryptographic digital signature. Transaction-specific statutory fields outside the supported domestic workflows still need separate implementation.
- The baseline Alembic migration covers the current schema. Existing unversioned databases are stamped only when all tables and columns match; older prototype schemas need a reviewed data migration. PostgreSQL schema changes in future releases must be added as new Alembic revisions, with a backup and restore rehearsal before upgrade.
- Split allocations use a new additive table. Older application builds do not read those allocations, so after split payments are posted, restore from a verified backup or migrate the allocations before returning to an older build.
- Recovery codes, session revocation, request limits, partial bank matching/unmatching and dated reconciliation reviews are implemented. Tamper-resistant external audit retention, deployed and monitored offsite backups, and clean-host operational acceptance remain deployment work. A manual backup and restore drill was run in the isolated local Docker test stack; the encrypted offsite scripts were tested with real encryption and simulated database and storage commands.

Run the 45 API tests with `python -m unittest test_api test_vyapar_posting test_completion -q` from `backend`. Run the frontend build with `npm run build` from `frontend`.

### Advance payments

Non-GST companies can record customer and supplier advances from Payment in/out. Advances post to separate liability/asset accounts. Applying an advance to a posted invoice or bill creates a dated journal, updates outstanding balances, and retains the original payment. Applications require a retry key, company write access, matching party, sufficient available advance and document balance, and an open application date on or after both source dates. Advance balance reports support as-of dates and PDF/XLSX export. Regular GST service advances support tax-bearing receipts, partial applications and refunds. The server retains separate advance and tax postings; special statutory advance cases outside these workflows are not automated. Verified supplier advances imported from Vyapar can be applied to matching bills. Older app builds do not understand advance applications; use a reviewed migration/restore before rolling back after posting them.

### Reference document layouts and Vyapar backups

Settings includes Modern, Vintage, MRP + Discount, Elegant and Evergreen layouts adapted from the supplied screenshots, with synthetic sample PDF previews. They are functional adaptations, not pixel-identical reproductions. Branding supports PNG/JPEG logos and signature images, bank details, UPI QR, notes and terms. New documents snapshot these details. MRP is an optional display reference; selling rates remain tax-exclusive. Uploaded signature images do not create a cryptographic digital signature. Existing layouts remain available for compatibility.

The Vyapar importer accepts a single unencrypted ZIP/SQLite .vyb backup under 3 MB, with bounded expansion and row counts. Settings offers full posting or masters/source archive only. Both require owner access. Full posting requires an empty target, or masters from this same backup with empty ledgers, banks and stock. Preview writes nothing; commit is atomic and exact-file retries cannot duplicate transactions. Unsupported types, statuses, openings, adjustments, secondary units and valuation mismatches block posting.

The full posting adapter is verified against the supplied Apex Integrations backup: 33 sales invoices, one purchase, three receipts, 27 estimates and three purchase orders. Paid-at-invoice amounts become allocated receipts/payouts; later receipts retain their source links. Purchase-order payments post as supplier advances, including split cash/bank payments, without posting purchases, stock or input GST. Converted estimates stay closed, including source ID 35 whose destination link is missing. All 84 source stock balances are reproduced, including 35 negative quantities and their source zero values. Replenishing imported negative stock recognizes the cost of earlier shortages separately from inventory remaining on hand.

Document GST components post in whole paise. Original line-tax precision is retained. Vyapar's party GST report groups raw tax before rounding; five party subtotals differ by INR 0.01–0.02 from document-component postings and the differences cancel overall. The preview and saved reconciliation show these differences. Input GST remains pending review. Original scalar source tables are archived; binary images, attachments, user accounts and app settings are not migrated. This adapter does not promise support for every Vyapar backup version or transaction variant. The older Ace backup test covers masters/source archiving only.

Install test dependencies with `pip install -r backend/requirements-dev.txt`; run `python -m unittest test_api test_vyapar_posting test_completion -q` from backend (45 tests). `verify_vyapar_posting.py` rehearses a private backup in a disposable local database and can compare native transaction, stock and GST XLSX exports. `verify_vyapar_export.py` independently checks a company JSON downloaded from the hosted app. See [the posting report](APEX_VYAPAR_POSTING_REPORT.md) for committed target evidence, preserved source issues and exact reconciliation figures.


## Native clients and current UI release
